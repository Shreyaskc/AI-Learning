Chapter 19: Projects, mastery gates and interview practice. Four projects with concrete deliverables.

The following are learner assignments. The included synthetic labs give you starting mechanisms and recorded examples, not completed production capstones. Pick one project, produce its evidence, then use the rubric for feedback.

Project A , A trustworthy tabular predictor. Use synthetic support tickets or a documented public dataset. Define decision time, target maturity and costs. Implement a constant and rule baseline, logistic model and a tree-family comparison using an optional pinned library environment. Split by time or entity as justified; fit preprocessing inside training only. Deliver data contract, model comparison, uncertainty, slices, threshold selection on validation, a frozen final test report, and a script that reruns it. This extends the standard-library lab; the repository now includes a synthetic trained tree and logistic and multilayer perceptron comparison; extend it to public data and library implementations rather than treating the synthetic report as real-world validation.

Acceptance: no future fields, no final-test tuning, reproducible artifacts, error analysis that leads to a next experiment, and a clear explanation of where the data is unrealistic. Counter-test: inject a post-outcome feature and demonstrate why an apparently excellent score is invalid.

Project B , A cited knowledge assistant. Build ingestion, lexical baseline, optional dense retrieval and reranking, access control list enforcement, provenance and deletion. Add a generator only after retrieval evaluation. Include answerable, unanswerable, conflicting, stale and adversarial documents. Report retrieval recall and ranking separately from citation support, answer correctness, abstention, latency and cost. Use synthetic data by default; optional provider calls require separate configuration and budget.

Acceptance: an unauthorized document never enters model context; generated claims carry supporting evidence or are withheld; deletion invalidates derived records; human-rubric evaluation includes disagreements. Counter-test: a highly relevant unauthorized page and an authorized page containing malicious instructions.

Project C , A bounded operations assistant. Start with read-only diagnosis and a fixed state machine. Compare a model-selected next-step variant only if task variability justifies it. Enforce schemas, allowlists, budgets, durable operation identifiers and audit logging. Simulate timeouts, duplicate requests, unknown tools and stale state. Deliver transition diagram, retry policy, recovery trace, threat model and incident report.

Acceptance: the assistant stops at its budget, repeated operation identifiers do not duplicate effects, ambiguous timeouts trigger status checks, and sensitive changes follow explicit authorization policy. Counter-test: crash after effect but before acknowledgement; demonstrate recovery without repeating the effect.

Project D , A serving and platform design with measurements. Begin with a small local mock service and load generator, then optionally a real C P U and G P U model. Measure queueing, throughput and tail latency for different prompt and output lengths. Estimate weight and key value memory, choose admission and batching policy, record versions, define SLOs and practice rollback. Declare whether measurements come from a mock or real model; never label mock tokens per second as G P U throughput.

Acceptance: capacity arithmetic is dimensionally correct, overload degrades predictably, tenant quotas work, cost per successful task is defined, and rollback returns to a compatible data and model and index set. Counter-test: one tenant sends long contexts that would exhaust shared memory.

Each project needs a README, clean run instructions, provenance, tests, evaluation report, architecture and dataflow, assumptions, limitations, resource estimate and five-minute defense. These are assignments; the tiny course labs are starting mechanisms, not completed production capstones.
